# Root Cause Protocol · 根因协议（5 Whys + 占位符替换测试）

> 一句话：**修「根」不修「表象」。表象消失 ≠ 根因消失，占位符替换测试是用来拆穿这句话的工具。**

## 一、为什么需要单独一条

`repeat-failure-breaker.md` 处理的是「同一个问题反复失败」的**流程**，
本文件处理的是「某一个具体缺陷」的**根**在哪一层。

典型事故形态：同一个 Issue 报修了 3 次，每次都"修好了"，第 4 次还炸。
根因：前 3 次修的全是**下游症状**，源头一次没动。

## 二、5 Whys（连问五层）

对失败现象连问「为什么」，每往上一层，答案必须**换一个对象**（换模块 / 换角色 / 换假设）。
如果第 N 层答案和第 N-1 层是同一个对象的同一个性质 → **没往上走，重问**。

```
现象：API 请求失败
① 为什么？        → JSON.parse 抛异常
② 为什么？        → provider 返回了 HTML 而不是 JSON
③ 为什么？        → baseUrl 被写成站点根地址，未指向 API 端点
④ 为什么？        → 配置面板缺少 baseUrl 合法性校验，任何字符串都能存进去
⑤ 为什么？        → 配置层没有「写入前验证」这条设计约束（← 根因）
```

第 ⑤ 层通常落在三类之一：

| 根因类型 | 特征 | 修法 |
|---|---|---|
| **设计缺口** | 根本没有这道防线 | 加约束 / 加默认 / 加护栏 |
| **契约不清** | 两边对同一字段理解不同 | 定契约 + 加断言 |
| **时序错误** | 顺序反了 / 用了过期快照 | 改时序 + 加失效标记 |

## 三、★ 占位符替换测试（区分真根因 vs 补丁）

> 这是本文件的核心工具。在声称「找到根因」之后、**动手之前**执行。

### 操作步骤

1. 把你认为的根因，写成一个陈述句 R
2. 把 R 里的**具体对象替换为占位符 `<X>`**
3. 自问：**「如果 `<X>` 换成任意同类事物，我的修复是否依然正确？」**
4. 判定：
   - **是** → 你修的是**通用约束**（真根因），放行
   - **否** → 你修的是**这一个具体值的特例**（补丁），退回第 ② 步往上再问

### 实例（对照上面的 5 Whys）

| 候选修复 | 占位符替换后 | 判定 |
|---|---|---|
| 「把这个 baseUrl 改对」 | 「把 `<任意字符串>` 改对」——换个用户又配错怎么办？ | ❌ **补丁**，退回 |
| 「面板加 baseUrl 校验 + 默认补 /v1」 | 「任意输入的 `<X>` 都要过校验」 | ✅ **真根因**，放行 |

### 第二个判据：反向复现

真根因必须能**正向解释全部已知现象**，且能在旧代码上被**复现**：

```
我声称根因 R 成立。那么在此之前观察到的现象 P1..Pn，
是否每一个都能被 R 推导出来？有没有哪个 Pi 是 R 解释不了的？
——有解释不了的 Pi → R 不完整，继续问。
```

## 四、输出格式（必须落盘）

```markdown
### Root Cause · IMP-xxx
现象：<用户可见的一句话>
5 Whys：
① … ② … ③ … ④ … ⑤ …
根因类型：设计缺口 / 契约不清 / 时序错误
占位符替换测试：
  R = <陈述句>
  替换后 = <带 <X> 的句子>
  判定 = 通用约束 / 特例补丁
反向复现：能解释的现象 P1..Pn（列出）；解释不了的（列出并说明）
修复层级：第 ⑤ 层，而非第 ① 层
```

## 五、常见陷阱

| 陷阱 | 表现 | 规避 |
|---|---|---|
| **停在技术层** | 5 Whys 全是代码细节，从不落到约束 | 第 ④ 之后必须换角色/换假设 |
| **循环论证** | ①②问到底又绕回现象 | 每层答案必须**换对象** |
| **把复现当根因** | 「能稳定复现了」就声称找到根因 | 复现是工具，不是结论 |
| **过早停在第 ① 层** | 「加个 try/catch 就完了」 | 加 catch 只能让现象消失，不能让 bug 消失 |

## 六、与判据链的关系

```
root-cause-protocol  → 确定「改哪里」
discriminating-test  → 证明「改了有效」（先失败后通过）
oracle-gate          → 禁止「自己说改好了」
```

三者串行，缺一不放行。
