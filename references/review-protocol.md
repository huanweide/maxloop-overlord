# 集体评审协议（MaxLoop 魔王系统 · 阶段二）

## 一、开会形式
全体 Agent 汇总各自深度体验报告，由 Chair 主持整合。整合不是简单拼接，而是：
- **去重**：相同问题合并为一条，标注全部提出者。
- **归类**：按模块 / 严重度归组。
- **初筛**：移除无证据支撑的臆测（无文件:行号或运行证据的一律不收）。

## 二、判据门槛（核心规则 · v3.0 起由「投票制」改为「证据制」）
- **收不收这条问题，取决于证据，不取决于票数。**
  - 投票制在 1-2 人时是纯仪式（2 人各 1 票 = 必须全票，1 人 = 必然通过），
    且会从众、会被资历压服——讨论的音量压过了判据本身。
- **每条入清单的问题必须同时满足**：
  1. **可追溯**：附 `文件:行号` 或可执行复现步骤；
  2. **可复现**：由提出者之外的人按该步骤独立复现成功；
  3. **对齐当前代码**：见第五节「结论漂移防线」——**未核销者不收**。
- **票数仅在多人并行评审（≥3 人）时用于排序优先级**，不用于决定收与不收。
- 反对意见须附理由（为何不认可），避免无理由否决导致遗漏真问题。

## 五、★ 结论漂移防线（2026-09-19 新增 · 血泪成本）

> 背景实证：一份 worker 产出的 24 项审查报告中，**经核实有 8 项的符号在当前代码里 0 命中**
> （`initTiku` / `processSchoolQuestion` / `quotaManager` / `emitImplementationMissing` /
> `isDevMode` / `_traded` 全库搜不到），另有 1 项（`handleAnswerDialog` 缺 wrapper）
> 描述的是**早已修复**的旧版本行为。
> 若照单全收去改，会在不存在的函数上"修"半天，或把已修好的代码再改坏。

### 强制流程（入清单前必须完成）

1. **符号核销**：报告里每个 `函数/变量` 名，用 grep 在**当前**工作树搜一遍，记录命中与否。
   - 0 命中 → **判定为漂移，直接废弃**，不进清单、不讨论。
   - 命中 → 继续第 2 步。
2. **行号核销**：报告标注的行号处的代码，必须与描述的行为一致。
   - 不一致（如描述说"缺校验"但该处已有校验）→ **已修复/已漂移**，废弃。
3. **产出核销表**：例如

```markdown
| 编号 | 报告声称 | 实际核实 | 判定 |
|---|---|---|---|
| C06 | LLM 返回 HTML → JSON.parse 炸 | 10-llm.js:78 确实如此 | ✅ 真 Bug |
| C01 | root() 取第一个 dialog | 已于 09-19 改为打分选优 | ❌ 已修复 |
| C02 | initTiku 四大 healer | 全库 0 命中 | ❌ 不存在 |
```

### 为什么必须写成流程而不是提醒
提醒依赖自觉，流程依赖产出物——**没有核销表不许开会**，漂移到不了清单里。

### 反模式
| 反模式 | 后果 |
|---|---|
| 「报告格式很专业，应该没问题」 | 专业格式与内容正确无关 |
| 「先改了再说，不对再说」 | 在不存在的函数上改 = 制造新 bug |
| 「旧报告至少指了个方向」 | 方向若基于旧版本，指的就是错路 |

## 三、改进清单格式
```
ID       来源 Agent   严重度   模块        问题描述（含文件:行号）        建议方向
IMP-001  <agent>     P1      确认流程    POST /api/... 空正文未拦截     src/core/confirm-guard.ts
```
- 严重度：P0 阻断（主流程不可用）/ P1 重要（功能缺陷或体验硬伤）/ P2 轻微（文案 / 细节）。
- 改进清单是阶段三的输入，须可追溯到原始报告与提出者。

## 四、输出
- 生成 `PROCESS/meetings/round-N/_integration.md`：整合报告 + 逐条投票结果（票数 / 认可者 / 反对理由）+ 改进清单（IMP-xxx）。
- 未入清单的问题单独归档为「观察池」，下轮复验时复核，不因一次未过半而永久丢弃。
