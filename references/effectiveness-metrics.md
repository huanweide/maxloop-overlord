# Effectiveness Metrics · 效果度量（让「数据提升作用」可量化、可累积）

> 一句话：**魔王系统的价值不能靠「感觉更稳了」来证明，必须把每次迭代的量化收益记下来。**

## 一、为什么需要

v3.1 之前的实证散落在各项目的 CHANGELOG 里，无法横向比较，也容易被误读成「玄学更稳」。
本文件把「提升作用」具象成 4 个必记指标，每一轮都要填——这是 v3.2 的**实质升级**，不是文案。

## 二、四个必记指标

| 指标 | 定义 | 怎么算 | 量化了什么价值 |
|---|---|---|---|
| **假绿拦截数** | 被 Oracle Gate 打回、本会被误判「修好」的修复数 | Oracle Gate 四行表填不全的次数 | 防假收敛能力 |
| **结论漂移核销数** | 审查报告里被符号核销判定为假靶而废弃的条数 | 核销表「❌」计数 | 不被无证据报告带偏 |
| **逃逸触发次数** | 进入 R2/R3/R4 的 IMP 数 | stuck 计数 ≥2 的条目 | 止损及时性 |
| **单轮有效修复数** | 当轮真正过 Oracle Gate 的 IMP（非补丁、非假绿） | 过 Gate 的 IMP | 真实 throughput |

## 三、记录格式

每轮末填表，落到会议记录 `PROCESS/meetings/round-N/_integration.md` 的「效果度量」段：

```markdown
### 效果度量 · round-N
| 指标 | 数值 | 备注 |
|---|---|---|
| 假绿拦截 | n | 例：Oracle Gate 打回的 IMP-xxx |
| 结论漂移核销 | n | 例：核销表 8/24 假靶 |
| 逃逸触发 | n | 例：IMP-xxx 进入 R2 |
| 有效修复 | n | 例：当轮归零的 IMP |
```

## 四、诚实原则（与铁律 5 一致）

- **查不到的数据写「未找到」，绝不填数。** benchmark 类要公开可复现。
- 单列「无效返工节省」时，必须用上轮对比，不得凭印象。
- 指标是**相对比较**（用 vs 不用魔王系统、上轮 vs 本轮），不是绝对分数。

## 五、实证基底（v3.0 真实数据，非编造，来自 zhihuishu-helper）

| 维度 | 没有魔王系统（v2.2 实证） | 用了魔王系统（v3.0 实证） |
|---|---|---|
| 迭代轮数 vs 收敛 | 6 轮全绿（358→421）问题依旧 | 判别测试确保每次修复 baseline 必红 / candidate 必绿 |
| 假绿 | 每轮「全绿」= 假绿，0 拦截 | 23 条判别测试全红，锁定真修复 |
| 无证据报告 | 审查报告照单全收 | 24 项审查核销 8 项假靶（33%） |
| 同问题返工 | 同一缺陷连修 6 轮（R1-R6 同马甲） | R2 即强制换人，禁止第 3 次同招 |

> 测试门禁随功能增长始终 0 失败：421 → 444 → 449 → 458。
